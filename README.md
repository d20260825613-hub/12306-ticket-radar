# 12306 余票雷达

只读的余票查询与微信提醒工具。**它不抢票** —— 下单始终由你在 12306 官方渠道手动完成。

---

## 先说清楚能力边界

| 做 | 不做 |
| --- | --- |
| 只读查询余票 | 不登录你的 12306 账号 |
| 监测余票变化并微信提醒 | 不识别/绕过验证码 |
| 采集 12306 网络时延 | 不自动提交订单 |
| 本地站点库（3384 站） | 不自动支付 |
| 余票变化历史记录 | 不做多账号、不做代理 IP 池 |

**为什么不做后一组**：它们违反 12306 用户协议；更关键的是，**第三方在 12306 的放票队列里没有任何优先级**。12306 是服务端排队放票，谁先到服务器谁先得，所谓"加速包"在技术上不存在插队机制。

### 一个必须知道的事实

截至 2026-09 实测，12306 给余票查询端点加了**客户端 JS 指纹校验**：

```
GET /otn/leftTicket/query?<参数>   → 302，告知当前端点名（如 queryG）
GET /otn/leftTicket/queryG?<参数>  → 302 → /mormhweb/logFiles/error.html   ← 被拦
```

这个拦截**与请求头无关**：即使用真实 Chrome 的全套 Ajax 头（`X-Requested-With`、`Sec-Fetch-*`、`sec-ch-ua`…）也一样被踢。静态资源（站名表、余票页）仍可正常访问。

本工具**不会去逆向这段校验** —— 那属于绕过技术保护措施，性质与"只读查询"完全不同。

**所以当前状态**：网络延迟监测、站点库、微信推送、变化检测全部可用；余票数据在 12306 放开前拿不到。程序会把拦截原因如实显示在界面上，不静默失败、不假装成功。

## 最快的中票路径（这才是重点）

```
官方候补购票（多车次 / 多席别 / 多日期全排上）   ← 主武器
        ＋
本工具（盯退票回流 + 微信提醒，你收到提醒后手动补一单）  ← 雷达
```

只靠手动刷、或只靠任何第三方工具，都不会比这个组合快。第三方工具真正能帮你的不是"抢得更快"，而是**让你不必一直盯着屏幕**。

## 运行

### 方式一：桌面 exe（已安装，推荐）

桌面上有两样东西：

| 名称 | 说明 |
| --- | --- |
| **`余票雷达`**（文件夹） | 自包含安装目录（28 个文件，410 KB）。**移动它程序照常运行**，不要只移 exe |
| **`余票雷达.lnk`**（快捷方式） | 指向 `余票雷达\余票雷达.exe`，已带上雷达图标 |

双击 `余票雷达.exe` 即可：定位 Node.js → 自检站点表 → 拉起本地服务 → 自动打开浏览器。
窗口里会实时打印服务日志；**关闭那个窗口就退出程序**。

程序需要 Node.js 18+。启动器按以下顺序查找：
`runtime\node.exe` → 环境变量 `TICKET_RADAR_NODE` → `%ProgramFiles%\nodejs` 等常见路径 → `PATH`。
如果都没有，到 https://nodejs.org 装 LTS，或把 `node.exe` 放进安装目录的 `runtime\` 子目录（可随目录一起分发，实现真正的绿色免安装）。

### 方式二：项目内启动器

双击项目根目录的 `start-radar.bat`（功能与 exe 相同，作为备用）。

> ⚠️ `start-radar.bat` **必须保持纯 ASCII**。cmd.exe 按 ANSI 读取 .bat，中文注释会破坏命令解析（实测踩过这个坑）。
> 同理，**不要用 Windows PowerShell 5.1 的 `Get-Content`/`Set-Content` 改写任何含中文的 `.js`/`.ps1`** —— 会按 ANSI 读写导致中文损坏。

### 方式三：命令行

```bat
node src\server.js
```

面板地址 `http://127.0.0.1:12308/`，只监听本机，不对外暴露。

### 重新构建 exe

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build_exe.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build_exe.ps1 -InstallDir D:\somewhere
```

用 Windows 自带的 .NET Framework 编译器 `csc.exe` 编译 `tools\Launcher.cs`（无需 SDK），
自动生成图标（`tools\make_icon.ps1`、`tools\make_launcher_icon.ps1`）、暂存安装目录、建快捷方式。

**这个 exe 不是单文件** —— 它是一个 28 KB 的启动器 + 一个需要同目录 `src`/`web`/`data` 的应用目录。
之所以这样：`web/` 页面和 `data/station_name.js` 必须能从磁盘读取，打包成单文件反而更脆。
单文件方案（Node SEA，约 90 MB）仍可行，见下方待办。

## 数据源（决定能不能看到余票）

这是本项目最关键的一环，必须说清楚。

### 为什么需要配置

12306 的余票查询接口在 **2026-09** 之后加了**客户端 JS 校验**：非浏览器请求会被
302 重定向到 `/mormhweb/logFiles/error.html`。实测即使带真实 Chrome 的全套 Ajax 头
（`X-Requested-With`、`Sec-Fetch-*`、`sec-ch-ua`…）也一样被拒。

复现命令：

```bat
node tools\probe_datasource.js
```

**本工具不会去逆向这段校验** —— 那属于绕过技术保护措施，性质与"只读查询"完全不同。

### 可用方案：第三方合规数据源

| | 说明 |
| --- | --- |
| 平台 | [接口盒子 apihz.cn](https://www.apihz.cn/user/) |
| 费用 | 免费，**10 次/分钟、每日无上限**（个人盯票完全够用） |
| 需要什么 | 注册后从「个人资料」复制 **开发者ID** 与 **开发者KEY** |
| 合规 | 平台自行维护取数通道（含平台侧会话），责任留在平台侧；使用者只需注册自己的 id/key |
| 实测状态 | 服务正常，平台自检历史成功率 **99.98%**（167339 成功 / 35 失败） |

配置入口：**设置 → 数据源**，填入两个参数后点「测试连接」。
测通会**自动保存**，之后余票就会正常显示。

> 平台另有[付费商业接口](https://market.aliyun.com/detail/cmapi00071386)（阿里云云市场，聚美智数），
> 有正式商业资质，需要更高稳定性或商用授权时可考虑。

### 架构

数据源被抽象成可替换的 provider（`src/core/providers/`）：

```
providers/
├─ index.js   选择逻辑：auto / 强制 direct / 强制 apihz，含降级
├─ direct.js  直连 12306（当前不可用，保留以备其恢复）
└─ apihz.js   第三方数据源（含返回结构归一化）
```

统一契约：`fetchTickets({date, from, to, cfg})` → `{ok, rows, source, error}`，
`rows` 与 `src/core/parser.js` 的输出**同构** —— 因此变化检测、微信推送、
界面渲染这些上层逻辑完全不用改。

`auto` 模式的语义：优先直连（数据最一手），不可用时自动改用第三方（前提是已配置）。


界面「设置」页填入 token，点「发送测试」即可验证。

| 通道 | 获取方式 | 备注 |
| --- | --- | --- |
| **PushPlus**（默认） | [pushplus.plus](https://www.pushplus.plus) 微信扫码 → 「一对一推送」复制 token | 免费，服务号推送 |
| Server酱³ | [sct.ftqq.com](https://sct.ftqq.com) 微信扫码 → 复制 SendKey | 备选 |

token 只存在本地 `data/config.json`，不进代码、不上传。

## 时间与日期的显示

时间信息最容易"看起来对、实际看不懂"，所以做了几处刻意的人性化：

| 场景 | 显示 | 为什么 |
| --- | --- | --- |
| 今天的日期 | `今天 周六` | 省得在脑子里换算 |
| 明天 / 后天 | `明天 周日` / `后天 周一` | 同上 |
| 更远的日期 | `09-26 周六` | 带星期，不用查日历 |
| **跨零点到达** | **`次日 08:44`**（橙色） | Z/T/D 字头夜车出发 19:10、到达 08:44 —— **不标"次日"会让人以为票错了** |
| 历时占位值 | `—` | 平台对"当日不开行"会返回 `99:59`，显示成"99 小时"很荒谬 |
| 事件文案 | `G1 06:30→11:24 二等座 无票 → 有(12)` | 比只写"06:30开"更容易对上是哪一趟 |
| 微信推送 | 日期带星期、到达标"次日" | 手机上看消息时同样需要 |

跨零点判断规则：**到达时刻的分钟数小于出发时刻** 即视为次日。
占位时刻 `24:00` 不参与判断（那是"当日不开行"的占位值，已被过滤）。

实测覆盖（北京→上海，含大量夜车）：

```
1461  11:59 → 次日 06:45   历时 18:46
D17   19:10 → 次日 07:31   历时 12:21
Z281  19:10 → 次日 08:44   历时 13:34
D7    19:18 → 次日 07:25   历时 12:07
D9    19:36 → 次日 08:00   历时 12:24
T109  20:04 → 次日 11:02   历时 14:58
```

## 余票数量的显示

余票有三种状态，**必须区分清楚**，否则极易误读：

| 状态 | 界面 | 含义 |
| --- | --- | --- |
| 明确无票 | `二等 无` | 没有余票 |
| 有票且有具体数量 | **`12 二等`**（数字加粗放大） | 余票 12 张 |
| 有票但平台未公布数量 | `二等 数量未公布`（虚线框） | **有余票，但不知道剩几张** |

第三类最容易被当成"没数据"或"没票"，所以显式写出"数量未公布"，并在列表上方给出统计摘要。
有确切数量的席位会**排在前面**，方便先看到能确定的。

**平台实际给多少数字**（实测北京南→上海虹桥，一次采样）：

```
明确无票           407 个席位
有票但数量未公布    101 个席位
有具体数量          42 个席位   ← 如 商务座 11 张、一等座 8 张
```

也就是说"有确切数量"只占少数 —— 12306 对部分席位只公布"有/无"。
这不是本工具的缺陷，是数据源本身的粒度。

## 频率设计（刻意的保守）

- 常态 **60 秒**一次；整点放票窗口（8:00–18:00 每小时前 3 分钟）提速到 **20 秒**
- 余票库本身不是实时推送，秒级轮询**不提升中票率**，只会提高被风控的概率
- 变化检测只在「无票→有票」「余票增加」时提醒，并按车次+席别+变化类型去重，避免刷屏
- 静默时段（默认 23:00–06:00）只记录不推送

| 问题 | 症状 | 修复 |
| --- | --- | --- |
| **默认查询 45 天，超出预售期必然失败** | 界面日期选项是 7/15/30/45 天且默认 45；而 12306 预售期约 14 天，**实测第 15 天起平台一律返回"查询失败"**（连付费档也一样）。于是「测试连接」用 7 天能成功、实际采集用 45 天必然失败 —— 用户看到"测试有结果但刷新没结果" | 日期上限统一为 14 天：provider 层 `clampDate()` 自动收敛超限日期、界面选项改为 1~14 天、服务端收敛超限输入、**启动时自动修正历史配置里的超限线路并告警** |
| **平台上"当日不开行"的占位记录会混进列表** | 当日不开行的车次返回时刻 `24:00/24:00`、历时 `99:59`、全部席位为 0（如北京南→上海虹桥里的 G531）。展示出来就是一趟时刻乱码又永远没票的幽灵车次 | `isPlaceholderTrip()` 识别并丢弃；同时保留"时刻异常但确实有票"的记录，避免误杀跨零点车次 |
| **引导卡按钮渲染了却没绑定处理函数** | `viewRadar` 在"还没有采集到数据 / 没有车次"两个分支**提前 return**，而绑定代码写在函数末尾 —— 于是「去填写数据源」按钮显示出来但点了毫无反应，用户**进不了填 KEY 的界面** | 抽出 `bindGuidanceActions()` 并在每个渲染分支都调用 |
| **没有监控线路时没有数据源入口** | 首次引导卡只有「添加监控区间」，而新用户往往先去配数据源 —— 此时页面上无处可点 | 引导卡增加「先去配置数据源（填 KEY）」，并提示"不接数据源加完线路也是空的" |
| **运行中的实例会锁住 exe 导致构建失败** | 程序运行时其 exe 被占用，`Copy-Item` 抛 `IOException` 中断整个构建 | 拷贝 exe 失败只告警；`web/`、`src/` 已更新，刷新页面即生效 |
| **弹层关不掉（CSS 层叠）** | 弹层是 `<div class="mask" hidden>`，而 `.mask` 上有 `display:flex`。样式表里**没有通用的 `[hidden]` 规则**，只靠浏览器默认样式，被 `.mask{display:flex}` 压过 —— 弹层一旦打开就永久卡住 | 加 `[hidden] { display: none !important }` 与 `.mask[hidden], .modal[hidden], .ac[hidden]` 兜底；并加断言锁死这条规则 |
| **改了 web/ 却忘了重建安装目录** | 修复只落在项目目录，运行中的实例一直提供旧文件，界面上完全看不出异常（这次导致"弹层关不掉"的修复没送到） | 新增 `tools/audit_dom.js`：对比线上文件与源文件，不一致就直接报出来并给出重建命令 |
| **绑定失败导致整片按钮失效** | `bind()` 是平铺赋值，任何一个元素缺失或赋值抛错，后面所有绑定全部跳过 —— 表现是"按钮点了没反应"却没有任何报错 | 引入 `safeBind()` 分组包裹，失败时 `console.error` + toast 提示；并注册 `error` / `unhandledrejection` 全局监听 |
| **关闭窗口后服务仍在后台运行** | 启动器用 `Process.Start` 拉起 Node，但 **Windows 不会因父进程结束而结束子进程**。点窗口的 × 后 Node 继续占着端口，下次启动看到"服务已在运行"，进程也清不掉 | 引入 **Job Object + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`**：子进程纳入作业对象，启动器一结束内核即连带结束它；再加 `CancelKeyPress` / `ProcessExit` 显式收尾 |
| **命令行端口参数没传给 Node** | 启动器接受 `余票雷达.exe 12309` 并用它做占用检查，但拉起 Node 时**没设 `PORT` 环境变量**，Node 仍用默认 12308 —— 端口参数形同虚设，还撞上其它实例 | 把端口写进子进程环境变量；端口优先级明确为 命令行 > `PORT` 环境变量 > 配置文件 > 默认 |
| **输出被重定向时启动器崩溃** | `Console.OutputEncoding = ...` 在无控制台句柄（日志重定向等）时抛 `IOException: 句柄无效`，启动器直接崩 | `InitConsole()` 包住所有控制台设置，并用 `GetConsoleWindow`/`GetStdHandle` 判断是否真有控制台 |
| **重新构建安装目录会让运行中的实例页面全 404** | `build_exe.ps1` 先 `Remove-Item` 整个安装目录再重建。正在运行的实例 API 还活着（模块在内存里），但静态文件是**按请求从磁盘读**的，目录一没就全是 404 | 改为**原地更新**：只清空子目录内容、保留目录本身；并在脚本末尾断言没有产生 `data\data` 之类嵌套 |
| **裸 "not found" 无法判断故障** | 界面文件缺失时只返回 9 字节的 `not found`，用户无从知道发生了什么 | 新增 `webDirStatus()` 自检：目录/文件缺失时返回 **HTTP 503 + 中文恢复说明页**（含重启指引）；启动时也会在控制台预警；`/api/state` 增加 `web` 字段；目录恢复后无需重启即自动恢复 |
| **构建脚本含中文导致语法错误** | `build_exe.ps1` 注释里有中文全角引号，PowerShell 5.1 按 ANSI 读取时误当字符串边界，报 `Unexpected token '}'` | 整个脚本改为**纯 ASCII**，中文一律用 `[char]0x....` 码点构造（与 `make_icon.ps1` 一致） |
| **数据目录不可写会导致启动崩溃** | `ensureDir()` / `saveConfig()` / `saveState()` / `port.txt` 都是裸 `writeFileSync`，装到只读介质、受控文件夹权限、系统保护目录下直接 `EPERM` 崩掉整个进程 | 全部包裹并返回布尔值；失败时降级为只读模式 + 一次性可读告警，服务照常可用 |
| **改配置会额外打一次 12306** | `POST /api/config` 调用 `engine.restart()`，而 restart 会立刻跑一轮采集 —— 用户在设置页调一次间隔就多查一次 | 拆成 `restart()`（线路变化，立即采集）与 `reschedule()`（仅重排下一次，改配置用） |
| **首次采集可能刷屏** | `diffSnapshot` 在 `prevByCode` 为空 Map 时，`!prev` 对每行都成立，把当轮所有可购车次当成"新增" | 入口处判定无基线直接返回；`newTrain` 改用 `seenTrains`（历史已提醒车次）判定 |
| **配置未加载时抛异常** | `isQuietNow()` / `currentIntervalSec()` 直接解构 `config`，`null` 时 TypeError | 统一 `config || DEFAULT_CONFIG` 兜底 |
| **快照行缺少 seatList 会漏检** | 快照里只存 `seats`，若调用方传入快照行而非解析行，`row.seatList` 为 undefined 直接抛错 | 增加 `seatsToSeatList()` 从 `seats` 重建 |
| **浏览器启动失败会崩掉整个服务** | `server.js` 的 `openBrowser()` 未捕获 `exec` 的 `EPERM`，一个可选便利功能把主服务一起带崩 | 加 try/catch + `child.on('error')`；启动器改为设 `NO_OPEN=1`，由它自己开浏览器 |
| **端口被占用时未处理的 error 事件** | `EADDRINUSE` 直接以未捕获异常崩掉，没有可读提示 | 加 `server.on('error')`，给出占用提示与换端口方法 |
| **端口被别的程序占用会误开浏览器** | 启动器只测端口通不通，任何程序占用 12308 都会被当成"服务已在运行" | 新增 `IsOurService()`，用 `/api/state` 的字段校验服务身份 |
| **捆绑 Node 运行时优先级偏低** | `runtime\node.exe` 排在环境变量和硬编码路径之后，可能被机器上不兼容的旧版本顶掉 | 捆绑运行时提到最前，其次才是 `TICKET_RADAR_NODE` 与常见路径 |
| **定时器可能在 stop 后复活** | `start()` 里在途的 tick 完成后仍会续期下一个定时器 | 引入 `timerGen` 代号，`stop()` 递增使旧 tick 失效 |
| **下单链接参数被编码** | `&fs=北京南,VNP` 里的逗号被 `encodeURIComponent` 编成 `%2C`，12306 认不出，「去下单」点了无效 | 只对站名单独编码，逗号保持字面量 |
| **端点发现逻辑依赖硬编码** | 先打 `queryG` 会死循环；`queryG` 轮换失效后整条链路断掉 | 改为先请求规范入口 `/otn/leftTicket/query`，跟随 302 的 `Location`/`c_url` 发现真实端点 |
| **余票行字段错位** | 前 12 段含 `%0A`/`%2F` 转义，直接 `split('|')` 会错位 | 先整体 `decodeURIComponent` 再切分 |
| **socket 监听器泄漏** | keep-alive 复用连接导致 `MaxListenersExceededWarning` | 请求设 `agent: false`，不复用连接 |

## 界面设计取舍

这个工具的使用者是想买票的人，不是来读技术报告的。几处刻意的设计决定：

| 决定 | 原因 |
| --- | --- |
| **取数被拦时首屏给"你现在该做什么"** | 原来的做法是甩一大段技术报错（"端点返回风控跳转"、"不会逆向客户端校验"），用户看完仍然不知道该干嘛。现在优先给 4 步可操作指引（候补 → 放票时间点 → 分流思路 → 让它替你盯），技术细节折叠收起 |
| **网页里有「停止程序」** | 原来只能去找那个控制台窗口，网页上没有任何退出入口。现在有确认弹层，并会等端口真的不再响应才显示"已停止" |
| **车次号可点击复制** | 真实流程是"在这里看到哪趟有票 → 切到手机 App 搜车次"，所以复制比阅读重要 |
| **独立的「怎么抢到票」页** | 承认第三方工具在放票队列里没有优先级，并把最有用的官方能力（候补）讲清楚 —— 这比包装一个做不到的承诺更诚实也更有用 |
| **窄屏改卡片式** | 原来表格在手机上会横向溢出；现在 `<=860px` 时表头隐藏、每行变成一张卡片 |
| **配色与深色模式** | 微信绿主色；跟随系统深色模式 |

界面文案有两类自动检查（在 `smoke_ui.js` 里）：

- **必有的正向内容**：候补指引、放票时间点、分流思路、官方入口、能力边界声明
- **必无的承诺式措辞**：`自动抢票`／`自动下单`／`保证有票` 等。断言会排除被否定的表述（"不自动下单"是正确的能力边界）和拆穿式表述（"所谓'加速包'在技术上不成立"）
